# Spec: Non-Functional Requirements

## Purpose
Нефункциональные требования: производительность, надёжность, безопасность, масштабируемость.

## Requirements

### REQ-NFR-001: Производительность — Задержка

**Scenarios:**
1. **Отображение страницы мероприятия**
   - WHEN пользователь запрашивает GET /events/:id
   - THEN ответ возвращается за <= 300 мс (p95)

2. **Резервирование места**
   - WHEN пользователь создаёт резервирование
   - THEN операция completes за <= 500 мс (p95)

3. **Обработка платежа**
   - WHEN инициирован платёж
   - THEN результат возвращается за <= 2 сек (асинхронно)

4. **Обновление статусов мест**
   - WHEN статус места меняется
   - THEN все WebSocket-клиенты получают обновление за < 1 сек

### REQ-NFR-002: Производительность — Пропускная Способность

**Scenarios:**
1. **Пиковая нагрузка**
   - WHEN система испытывает пиковую нагрузку (старт продаж)
   - THEN система обрабатывает до 10 000 запросов/сек

2. **Одновременные пользователи**
   - WHEN 100 000 пользователей открыли сессии
   - THEN система поддерживает все соединения

### REQ-NFR-003: Горизонтальное Масштабирование

**Scenarios:**
1. **Add без даунтайма**
   - WHEN новый узел добавляется в кластер
   - THEN система продолжает работать без прерываний

2. **Stateless-сервисы**
   - WHEN запросы распределяются между узлами
   - THEN любой узел может обработать любой запрос

### REQ-NFR-004: Надёжность — Доступность

**Scenarios:**
1. **Целевая доступность**
   - WHEN система эксплуатируется в течение года
   - THEN uptime >= 99.95% (не более ~4.3 часов простоя)

### REQ-NFR-005: Консистентность

**Scenarios:**
1. **Строгая консистентность для билетов**
   - WHEN два пользователя одновременно бронируют одно место
   - THEN только один успешно бронирует
   - AND ни одно место не продано дважды

2. **Eventual consistency для статистики**
   - WHEN продажа совершена
   - THEN статистика обновляется в течение <= 5 секунд

### REQ-NFR-006: Отказоустойчивость

**Scenarios:**
1. **Авария узла**
   - WHEN узел выходит из строя
   - THEN система продолжает работать на оставшихся узлах
   - AND данные не теряются

2. **Автоматическое восстановление**
   - WHEN узел восстанавливается
   - THEN система автоматически его реплицирует

### REQ-NFR-007: Безопасность — Аутентификация

**Scenarios:**
1. **Защита токенов**
   - WHEN токен перехвачен
   - THEN система обнаруживает аномальное использование (IP mismatch, device fingerprint)

2. **Срок действия токенов**
   - WHEN accessToken просрочен
   - THEN система требует обновления через refreshToken

### REQ-NFR-008: Безопасность — Защита от Атак

**Scenarios:**
1. **XSS защита**
   - WHEN запрос содержит XSS-payload в теле
   - THEN система экранирует вывод и отклоняет опасные данные

2. **CSRF защита**
   - WHEN запрос приходит без валидного CSRF-токена
   - THEN система отклоняет запрос

3. **SQL-инъекции**
   - WHEN запрос содержит SQL-инъекцию
   - THEN система использует parameterized queries
   - AND отклоняет запрос

### REQ-NFR-009: Безопасность — Шифрование

**Scenarios:**
1. **TLS для передачи**
   - WHEN данные передаются между клиентом и сервером
   - THEN соединение использует TLS 1.2+

2. **Шифрование в покое**
   - WHEN данные хранятся в БД
   - THEN чувствительные поля (password, payment info) зашифрованы

### REQ-NFR-010: Логирование и Мониторинг

**Scenarios:**
1. **Structured logging**
   - WHEN происходит любое ключевое действие
   - THEN система записывает structured log: { timestamp, level, userId, action, details }

2. **Метрики производительности**
   - WHEN запрос обрабатывается
   - THEN система записывает метрику: { endpoint, duration, status, userId }

3. **Трассировка**
   - WHEN запрос проходит через несколько модулей
   - THEN система добавляет traceId для сквозной трассировки

4. **Алерты**
   - WHEN p95 latency > 300 мс на протяжении 5 минут
   - THEN система генерирует алерт в Grafana

# Spec: User Authentication & Authorization

## Purpose
Аутентификация пользователей через JWT + OAuth2, авторизация через RBAC, управление пользователями и ролями.

## Requirements

### REQ-USER-AUTH-001: JWT Аутентификация
Система должна аутентифицировать пользователей с помощью JWT-токенов.

**Scenarios:**
1. **Успешная регистрация**
   - WHEN пользователь отправляет POST /auth/register с email и password
   - THEN система создаёт пользователя с ролью по умолчанию (BUYER)
   - AND возвращает accessToken и refreshToken

2. **Успешный вход**
   - WHEN пользователь отправляет POST /auth/login с email и password
   - THEN система возвращает accessToken (TTL 15 мин) и refreshToken (TTL 7 дней)

3. **Обновление токена**
   - WHEN пользователь отправляет POST /auth/refresh с валидным refreshToken
   - THEN система возвращает новый accessToken

4. **Отказ в доступе при невалидном токене**
   - WHEN запрос содержит невалидный или просроченный токен
   - THEN система возвращает 401 Unauthorized

### REQ-USER-AUTH-002: OAuth2 Аутентификация
Система должна поддерживать OAuth2 для входа через внешние провайдеры.

**Scenarios:**
1. **Авторизация через OAuth2 провайдер**
   - WHEN пользователь переходит на /auth/oauth2/:provider
   - THEN система перенаправляет на провайдера авторизации

2. **Обратный вызов OAuth2**
   WHEN провайдер возвращает пользователя по callback
   - THEN система создаёт или находит пользователя по email
   - AND возвращает accessToken

### REQ-USER-AUTH-003: RBAC Авторизация
Система должна контролировать доступ на основе ролей.

**Roles:**
- `BUYER` — покупатель
- `ORGANIZER` — организатор
- `AGENCY` — агентство
- `ADMIN` — администратор платформы
- `SUPPORT` — оператор поддержки

**Scenarios:**
1. **Доступ по роли**
   - WHEN пользователь с ролью BUYER пытается получить доступ к /organizer/*
   - THEN система возвращает 403 Forbidden

2. **Административный доступ**
   - WHEN пользователь с ролью ADMIN пытается получить доступ к /admin/*
   - THEN система разрешает доступ

### REQ-USER-AUTH-004: Управление пользователями
Система должна поддерживать CRUD операции для пользователей.

**Scenarios:**
1. **Получение профиля**
   - WHEN авторизованный пользователь отправляет GET /users/me
   - THEN система возвращает данные профиля

2. **Обновление профиля**
   - WHEN авторизованный пользователь отправляет PATCH /users/me
   - THEN система обновляет данные и возвращает актуальный профиль

3. **Управление пользователями (ADMIN)**
   - WHEN пользователь с ролью ADMIN отправляет GET /admin/users
   - THEN система возвращает список пользователей с пагинацией

4. **Изменение роли (ADMIN)**
   - WHEN пользователь с ролью ADMIN отправляет PATCH /admin/users/:id/role
   - THEN система обновляет роль пользователя

### REQ-USER-AUTH-005: Аудит действий
Система должна логировать ключевые действия пользователей для ролей ADMIN и SUPPORT.

**Scenarios:**
1. **Логирование входа**
   - WHEN пользователь входит в систему
   - THEN система записывает событие audit_log: { action: 'login', userId, timestamp, ip }

2. **Логирование административных действий**
   - WHEN пользователь с ролью ADMIN изменяет роль пользователя
   - THEN система записывает событие audit_log: { action: 'role_change', adminId, targetUserId, newRole, timestamp }

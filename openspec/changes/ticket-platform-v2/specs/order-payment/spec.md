# Spec Delta

## ADDED Requirements

### Requirement: Real Payment Provider Integration

Система SHALL создавать платёж через подключаемого провайдера (sandbox по умолчанию) и переводить
заказ в `PAID` только после подтверждения от провайдера.

#### Scenario: Создание платежа
- **WHEN** покупатель отправляет `POST /payments/:orderId/intent`
- **THEN** система создаёт платёж у провайдера и возвращает идентификатор и ссылку/параметры подтверждения
- **AND** заказ остаётся в `PENDING_PAYMENT` до подтверждения

#### Scenario: Провайдер недоступен
- **WHEN** провайдер отвечает ошибкой при создании платежа
- **THEN** заказ остаётся `PENDING_PAYMENT`, места остаются `RESERVED`
- **AND** клиент получает 502 с кодом ошибки провайдера

### Requirement: Payment Webhook Processing

Система SHALL принимать подписанные вебхуки провайдера, проверять подпись и обрабатывать каждое
событие идемпотентно.

#### Scenario: Успешный платёж
- **WHEN** провайдер присылает подписанный вебхук об успешной оплате
- **THEN** заказ переходит в `PAID`, места — в `SOLD`
- **AND** в outbox пишется событие `events.order.paid`
- **AND** повторный вебхук с тем же `providerPaymentId` не меняет состояние и возвращает 200

#### Scenario: Неверная подпись
- **WHEN** подпись вебхука не совпадает с секретом
- **THEN** система возвращает 400 и не меняет заказ
- **AND** инцидент фиксируется в логах с `traceId`

### Requirement: Payment Refund Initiation

Система SHALL инициировать возврат средств у провайдера при одобрении возврата, сохраняя
идемпотентность по возврату.

#### Scenario: Инициация возврата
- **WHEN** организатор или поддержка одобряет возврат по оплаченному заказу
- **THEN** система создаёт `Refund` со статусом `REFUND_PENDING` и вызывает провайдера
- **AND** повторный approve не создаёт второй refund

#### Scenario: Отказ провайдера
- **WHEN** провайдер отклоняет возврат
- **THEN** refund переходит в `FAILED`, заказ остаётся `PAID`
- **AND** возврат остаётся `APPROVED`, а операция доступна для повторной попытки

# Нагрузочный тест бронирования

## Стенд

- Windows-ноутбук, Docker Desktop VM: **8 vCPU, 3.7 ГБ RAM**.
- PostgreSQL 15, Redis 7 и Kafka запущены локально в Docker; приложение — один процесс Node.js на хосте.
- `NODE_ENV=development`, лимиты троттлинга подняты (`THROTTLER_SHORT_LIMIT=1000000`, `THROTTLER_LONG_LIMIT=1000000`).
- Сценарий: `POST /api/cart` с уникальным местом на каждый запрос (реальная проверка Redis-локов и транзакции БД), 6000 заранее созданных мест.

## Команда

```bash
LOAD_CONNECTIONS=50 LOAD_DURATION=10 npm run load:booking
```

Скрипт сам создаёт событие, места и тестового покупателя, логинится, гоняет нагрузку и удаляет фикстуры.
Порог задаётся через `LOAD_P95_LIMIT` (по умолчанию 500 мс) и `LOAD_ERROR_RATE_LIMIT` (1 %); при превышении — exit code 1.

## Результат: 50 соединений, 10 с

| Метрика | Значение |
|---|---|
| Запросов | 2 749 |
| RPS | 275 |
| p50 | 161 мс |
| **p97.5 (используется как консервативная оценка p95)** | **316 мс** |
| p99 | 381 мс |
| max | 407 мс |
| Ошибки (non-2xx / transport) | 0 / 0 |
| Ответы | все `201` |

Порог p95 ≤ 500 мс выполнен (316 мс по p97.5, фактический p95 ниже).

## Граница насыщения

Дополнительные прогоны на том же стенде:

| Соединений | RPS | p50 | p97.5 | p99 | Ошибки |
|---|---|---|---|---|---|
| 80 | 287 | 243 мс | 502 мс | 523 мс | 0 |
| 100 | 288 | 311 мс | 504 мс | 538 мс | 0 |

Выше ~50 соединений пропускная способность упирается в один процесс Node.js и локальную БД: RPS почти не растёт, растёт очередь и хвост задержки. Ошибок и таймаутов нет — деградация плавная.

## Выводы

- Целевой p95 бронирования достигается при 50 конкурентных соединениях; 80–100 соединений находятся на границе порога.
- Для целевых 1000+ соединений нужен горизонтальный масштаб: несколько инстансов приложения, Redis-адаптер Socket.IO, пул соединений Prisma/БД и отдельный load-balancer.
- Узкие места: один event loop, транзакция бронирования (Seat update + Reservation insert) и сериализация запросов в PostgreSQL.
- `autocannon` не отдаёт p95 напрямую (в гистограмме есть p97.5), поэтому в отчётах используется p97.5 как более строгая граница.
